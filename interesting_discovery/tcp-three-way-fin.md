# TCP 三次挥手现象观察记录

## 背景
在学习TCP协议时，我使用本工具抓包分析连接释放过程，发现了一个与教科书“四次挥手”不同的现象。

## 抓包数据
TCP: 150.171.110.131:443 -> 10.0.2.15:55228
  Seq=521608713, Ack=2993442055, Data Offset=20
  Flags: FIN=1, SYN=0, RST=0, PSH=0, ACK=1, URG=0
  Window=65535

TCP: 10.0.2.15:55228 -> 150.171.110.131:443
  Seq=2993442055, Ack=521608714, Data Offset=20
  Flags: FIN=1, SYN=0, RST=0, PSH=0, ACK=1, URG=0
  Window=65535
  
TCP: 150.171.110.131:443 -> 10.0.2.15:55228
  Seq=521608714, Ack=2993442056, Data Offset=20
  Flags: FIN=0, SYN=0, RST=0, PSH=0, ACK=1, URG=0
  Window=65535

## 现象分析
第一个包 

Flags: FIN=1, ACK=1

这是服务器的第一次挥手。它说：“我已经没有数据要发了，请求关闭连接。”

第二个包 

Flags: FIN=1, ACK=1

这里发生了合并。“我收到了你的FIN（这是ACK的作用），并且，我也没有数据要发了（这是FIN的作用）。”

它把标准挥手流程中的第二次（ACK）和第三次（FIN）合并成了一个包。

第三个包 

Flags: ACK=1

这是服务器的第四次挥手。它说：“好的，我收到了你的FIN，连接彻底关闭了。”
## 结论
因为TCP的延迟确认机制和捎带确认机制在发挥作用。

延迟确认：当一端收到一个数据包（这里是FIN包）后，它不会立即发送ACK，而是会等一小段时间，看看有没有数据要“捎带”着发出去，以提高网络利用率。

捎带确认：在收到服务器的FIN后，恰好在等待期间发现自己也没有数据要发送了。于是，它就把“对FIN的确认（ACK）”和“自己的FIN请求”打包在一个TCP包里发了出去。

这就像两个人告别，一个人先说“我走了”，另一个说“好的，我知道了，我也正要走”——于是一句话完成了两件事。
